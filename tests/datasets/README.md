# Dataset isolation framework — M0-07 / ALG-01 preparation

Development implementation; formal review and the actual frozen acceptance corpus are still pending. Public `examples/` contains one synthetic **development** case, not calibration, regression, blind acceptance, or evidence of meeting PRD accuracy targets.

## Three separate data boundaries

1. Detector input (`schemas/detector-input.schema.json`, Go `Input`): opaque case ID and observable request/response/tokenizer snapshots only. Strict decoding rejects unknown fields at every level, including `labels`, `expected_risk`, `scenario`, and controller metadata. The detector receives only this input stream; `DecodeInput` never looks for companion files.
2. Controller manifest (`schemas/manifest.schema.json`, Go `Manifest`): case-to-split mapping, shared lineage, input SHA-256, coverage and optional freeze timestamp. This is also oracle-sensitive and must not be mounted in the blind detector process.
3. Owner labels (`schemas/labels.schema.json`, Go `Label`): independently reviewed conditions/rationale, joined to predictions only after detector output is sealed. Label examples are explicitly development-only.

The Go validators are executable constraints, not merely schema examples. `ValidateManifest` rejects repeated case IDs, repeated content hashes, malformed hashes, cross-split lineages and invalid coverage. `Fingerprint` hashes canonical samples without case/sample IDs so renaming identical cases does not evade isolation. Derived prompts, shared source batches, paired stream/non-stream variants, semantic paraphrases, repeated seeds and captures of the same upstream identity must share one owner-assigned lineage. Semantic near-duplicate detection is not automated; dataset-owner review remains required. `ValidatePartition` also checks actual input content hashes and exact membership; `ValidateLabels` rejects cross-split/duplicate/inconsistent labels.

## Partition rules

| Partition | Permitted use | Visibility and promotion |
|---|---|---|
| `development` | Implementation and exploratory tuning | Public synthetic examples allowed; never report as blind accuracy |
| `calibration` | Choose and freeze thresholds/weights | Visible only to calibration owners; cannot overlap development lineages |
| `regression` | Fixed CI replay after rule changes | Freeze independently; never tune against evaluation failures without recording a new version and refreshing acceptance holdout |
| `blind` | One sealed release evaluation | Release owner retains labels, manifest, scenario controls and fault seeds outside detector-author access; only opaque observations reach detector |
| `gray` | Approved, redacted real-world post-release observations | Requires separate credentials, budget, consent and human review; not auto-generated by this framework |

Each release partition must cover normal behavior, fixed caps, probabilistic/piecewise caps, hidden instructions, stream mutations, forged Usage, natural early completion, safety refusals, unknown tokenizers, reasoning models and high network errors. `ValidateCoverage` fails on an incomplete or empty partition; it verifies category presence, **not sufficient sample size, label correctness, model diversity or accuracy**. Coverage and sample-count requirements must be frozen with QA/ALG before formal evaluation. Cases can carry multiple conditions, but `normal` cannot coexist with deliberate mutation conditions.

Use opaque randomized case IDs and isolated endpoint IDs, model names, timestamps and seeds. Do not encode a scenario or expected class in detector-visible IDs/prompts. Keep request/model seeds needed for replay in observed inputs; never supply controller fault seeds, server snapshots or hidden configs. Label strings inside natural response content are untrusted observed text, not a privileged oracle field.

## Blind release procedure (not yet executed)

1. Independent release owner assembles held-out lineages and validates hashes, split isolation, coverage and labels. Keep the dataset/control repository private and outside this public workspace.
2. Freeze dataset, rule, template and tokenizer versions plus SHA-256; save the detector source/build commit and evaluation plan. Changing any of these starts a new evaluation version.
3. Run detector in a separate filesystem/user/container with read-only inputs only, no repository/controller/label mounts, no network access except explicitly isolated blind upstream endpoints, and no output channel to label owners during execution.
4. Seal prediction JSON and hashes before granting a separate evaluator label access. Compute confusion matrices and confidence intervals without tuning thresholds on held-out results.
5. Report all denominators, unavailable/partial cases, hard-negative false positives and exclusions. Compare fixed cap ≥95%, probability/piecewise ≥90%, stable hidden influence ≥85%, normal/hard-negative false positives ≤5%. Failure is not permission to move difficult cases out of the split or weaken the threshold.
6. If leakage or post-hoc tuning occurs, invalidate the run and create a new independently held-out dataset. Retain the invalidated evidence transparently.

Type/schema boundaries and import tests cannot create an actual blind environment when agents share one checkout. No private blind labels or claim of completed ALG-01 sign-off/ALG-04/M7-02 is delivered here. Actual owner-held datasets, access controls, frozen versions and blind execution remain required.

## Run

```powershell
.\.tools\go\bin\go.exe test ./tests/datasets ./tests/mock-upstream ./cmd/mock-upstream
```

CI tests reject labels at nested input boundaries, trailing JSON, altered samples, renamed exact duplicates, shared lineage across partitions, label crossing, unsupported tokenizer counts and contradictory labels. A production-import guard prevents `internal/**` or `cmd/mii` from importing this controller package or mock upstream. Mock helpers are allowed in test files. These checks complement, rather than replace, release-owner isolation review.
