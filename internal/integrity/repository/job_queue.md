# Database queue contract

`Store.OpenJobQueue` creates one opaque process consumer capability. PostgreSQL allows multiple consumers and uses `FOR UPDATE ... SKIP LOCKED` on candidate jobs and their organization fairness rows. SQLite grants one database-persisted, cross-process consumer lease; a second live consumer fails instead of silently sharing the file. Runtime must still enforce SQLite's single `all` process policy and stop/drain handlers before closing the queue.

Every job lease is 60 seconds. Worker integration must heartbeat every 15 seconds, including idle consumer heartbeats in SQLite. PostgreSQL lease times come from the database clock, avoiding Worker host-clock skew. Renewal, completion and retry require the current owner, current attempt generation, running state and an unexpired lease. Recovery increments the generation. A stale handler cannot complete even if the same process later reclaims the job. A failed database operation never fabricates an in-memory claim or completion.

`Tenant.Enqueue(JobSpec)` accepts known job types plus organization-scoped object IDs and non-sensitive scheduling fields only; no generic JSON/header/body payload exists. The object is verified before enqueue and again before dispatch. Reused idempotency keys return the original matching job without moving its schedule or changing completed results; changed type/object/priority/attempt limits conflict. Forged/unknown object references are failed without reaching handlers. A run/sample handler must still recheck its domain-specific state, cancellation and budget before each network operation.

`Tenant.InTransaction` supplies a callback-scoped `TenantTransaction`; `Enqueue` is currently its first typed operation. Run/sample persistence should extend this capability in the repository, not expose raw GORM handles. `JobQueue.CompleteWith` uses the same scoped capability for business changes and dependent jobs in one fenced transaction, with a second expiry check after the callback. Callbacks must be short database-only operations and cannot be used after return.

Ready organizations are ordered by last service time, then jobs by priority, availability and stable ID. This prevents one backlogged organization from taking every serial dispatch while preserving priority inside an organization. Recovery/terminal reconciliation works in bounded batches of 100; poison dispatch validation is bounded to 20 per poll. Cancelled pending jobs are not dispatched. Exhausted or malformed expired jobs become terminal, while normal expired jobs are eligible for recovery. Retry timing respects the caller's normalized delay (0–24 hours) and stores error codes only, never raw upstream error text.

Migration `000002_queue_leases` adds consumer/fairness tables and seeds existing jobs. Migration `000001` is unchanged. Current workers require the exact compiled schema; compatible rolling upgrades remain M6-04 work, not a solved guarantee here.

Verification covers real SQLite and PostgreSQL: concurrent/idempotent enqueue, transaction rollback, concurrent claims/completion, cross-process SQLite exclusion, PostgreSQL skip-locked behavior, owner/generation fencing, renewal, expiry/recovery, retry limits, delayed jobs, tenant fairness, poisoned tenant references, database outages and upgrade from an existing version-1 job. Expiry tests force persisted deadlines into the past instead of sleeping for a minute. End-to-end crash recovery timing, uncertain upstream Attempts/budget accounting, dispatch concurrency limits, full cancellation latency and Worker handlers remain M2/M7 integration work. Queue delivery is at least once; it does not claim exactly-once external HTTP execution.
