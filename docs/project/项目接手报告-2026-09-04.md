## 1. 产品目标理解

本项目是独立部署的模型服务黑盒完整性检测系统。系统通过 OpenAI-compatible Chat Completions API 使用合成探针进行重复、对照和统计实验，重点识别：

- 未知高优先级指令造成的稳定可观测行为影响；
- `max_tokens` / `max_completion_tokens` 不生效、被覆盖或存在固定/概率上限；
- SSE 提前中断、异常 EOF、缺少终止事件和流/非流不一致；
- Usage、`finish_reason`、模型回显和实际可见输出之间的矛盾；
- 固定响应前缀、后缀、免责声明、身份声明或代理改写。

产品结论必须表述为风险指数、置信度、证据等级和替代解释。纯黑盒结论最高为 B 级；模型自述权重恒为 0；没有直接网关证据时不得表述为已确认篡改或欺诈。

## 3. 技术架构摘要

- 单仓库；Go 后端和 React + TypeScript + Vite 管理端。
- 同一 Go 二进制可承载 Control API、嵌入式静态前端、Worker 和 Analyzer；`APP_ROLE` 控制部署角色。
- 单机使用 SQLite；标准生产使用 PostgreSQL。
- 核心队列使用数据库 Job + 租约；不强制依赖 Redis、S3、OIDC 或 KMS。
- 外部调用经 Safe HTTP Client，执行协议限制、DNS/IP 校验、连接固定、重定向复检、TLS 和响应大小限制。
- API Key 使用主密钥 + 每 Secret 数据密钥 + AES-256-GCM 信封加密，只写不可回显。
- Adapter 负责协议，Probe 负责实验设计，Analyzer 负责判断，Scoring 负责聚合；规则、模板、评分和 tokenizer 配置全部版本化。
- 报告以不可变 JSON 快照为事实源并渲染 HTML，保留版本、证据引用、限制、免责声明和内容哈希。

## 4. 关键风险

1. PRD 与 TECH SPEC 的待决策项尚未获得正式批准，不能把评审稿直接当作冻结版本。
2. `RUN-008` 被标为 P1，但 MVP 功能验收要求探针复测，存在优先级冲突。
3. TECH SPEC 发布 Runbook 中的 Redis/KMS 可用性检查及“功能开关默认关闭”与独立产品基线冲突，需要澄清为条件项。
4. Git 工具链不可用会阻塞 M0-03 仓库初始化及后续提交证据，需在进入 M0-03 前安装或提供可执行路径。
5. SQLite 与 PostgreSQL 的事务、锁和 JSON 方言差异较大，迁移和 Repository 必须从 M1-01 起双库验证。
6. Key 泄漏、SSRF、跨组织 IDOR 是发布硬门槛，必须从设计、日志、测试数据和 CI 全链路控制。
7. 算法指标依赖严格隔离的开发/校准/回归/盲验收数据；若标签泄漏或同集调参，准确率结论无效。
8. 模型随机性、自然 EOS、安全拒答、未知 tokenizer 和不可见 reasoning token 均可能导致误报，规则必须报告效应量和替代解释。

## 5. 待确认决策

完整建议见 `docs/decisions/M0-01-V1.0-决策记录.md`。需要 PO/TL 正式批准的核心事项包括：

- V1.0 按多组织数据模型和组织隔离交付；
- UI 使用“模型完整性风险指数”，不使用确定性“掺水率”；
- 完整响应正文默认加密保留 30 天，可配置为 0～180 天；
- 内网 Endpoint 默认禁止，仅管理员 CIDR 白名单可放行；
- 周期复检、PDF/CSV、Helm、规则签名列入 V1.1/P1；
- V1.0 的可信基线凭证和费用由各组织自行承担；
- 不自动停用目标或改变外部生产流量；
- SQLite 只定位为小规模单机模式，标准生产必须 PostgreSQL；
- 文件/容器 Secret 主密钥是必备默认能力，KMS 仅为可选适配器；
- 探针复测按 MVP 验收要求提升为 V1.0 范围；
- Redis/KMS 发布检查只在相应可选适配器启用时执行。
